# Надёжность выполнения задач

Разбор исходников 9 октября 2026. Проверен путь `run_turn` → LLM → dispatch → запись → события UI.
Доработки проверены offline тестами и отдельным прогоном реальной локальной Gemma 4 26B.
Все live задания выполнялись во временных папках, без производственного демона и его настроек.

## Подтверждённые проблемы и исправления

| Проблема | Последствие | Изменение |
|---|---|---|
| `tool_edit_lines` обрезал диапазон и замену до 30 строк | Успешный ответ означал лишь частично применённую правку, файл мог стать некорректным | Весь допустимый диапазон применяется за один вызов; выход за конец файла отклоняется до записи |
| `append_file` требовал минимум 8 строк или 200 байт | Небольшое необходимое дополнение отклонялось | Допускается любое непустое добавление |
| Редактор запрещал заголовки, версии и уменьшение текста по эвристике | Корректные текстовые правки и сокращения кода блокировались | Эти ограничения сняты; проверка уникальности фрагмента, границы workdir и backup сохранены |
| Ключ повторного вызова не содержал новый текст | Разные правки одного диапазона и разные добавления считались циклом | Сравниваются все аргументы с нормализацией порядка JSON-ключей |
| Цикл требовал минимум три записи после большого числа шагов | Готовая задача продолжалась с лишними изменениями | Квота записей удалена |
| Слова «канон»/«все файлы» включали продолжение по шаблону веб-проекта | Агенту навязывались `index.html`, `style.css`, `main.js`, `core/`, `apps/` | Продолжение по чужой структуре удалено |
| При первом ответе без tools цикл мог сразу закончиться | Обещание заменить файл оставалось обещанием | При запросе действий без успешных правок — до двух дополнительных попыток; при отсутствии записи финал прямо сообщает об этом |
| Промпт требовал записи после 1–2 разведок и роста файлов | Агенту мешали изучить зависимости и сделать минимальное исправление | Промпт требует действий по задаче, достаточного чтения, проверки результата и честного отчёта |

Остаётся защита от почти пустой замены большого диапазона строк. `create_file` не перезаписывает
существующий файл. Подтверждения опасных действий и настройки read_only не изменены.

## Проверка

`bash scripts/ci.sh`: сборка, offline ctest, закон дерева, qmllint и лимит размера модулей.
Тесты lifecycle/audit и новая проверка turn-execution используют локальную тестовую LLM,
поэтому окружение должно разрешать сокеты на loopback.

Новые сценарии проверяют:

- полную замену 50 строк и отказ при неверном диапазоне;
- небольшое добавление и обычную смену текста заголовка;
- различие ключей разных правок при одинаковом пути и диапазоне;
- семь чтений → одна достаточная правка → завершение без квоты;
- ранний текстовый ответ → повторная попытка → реальная правка;
- четыре последовательных небольших добавления в один файл;
- модель, не вызывающая инструменты: честный финал без утверждения об изменении файла.

## Доработки второго прохода

- Полный текст текущего задания закреплён в system prompt и не теряется при сжатии.
  Сводка сохраняет последние указания, подтверждённые изменения и ошибки. Повторное
  сжатие объединяет прежнюю сводку с новыми результатами, а не забывает её.
- Результаты tools получают явные `OK`/`ERROR` в контексте модели. Список «Изменены»
  строится только по успешным результатам, связанным с конкретными вызовами.
- Очередь разрешает чтение зависимостей и учитывает их успешные правки вне порядка.
  Добавлен `file_pass_review(path, note)`: прочитанный корректный файл можно завершить
  без искусственной записи. Проверки хранятся отдельно от записей в SQLite и передаются UI.
- Намерение хранится в состоянии хода как признаки необходимости tools, ожидаемых правок,
  запрета изменения и запрета создания. Распознавание команд использует границы слов;
  объяснение, стих или вопрос «как исправить» больше не требуют записи на диск.
  Явный запрет редактирования включает read_only на весь ход.
- Путь без аргумента восстанавливается по уникальному совпадению фрагмента прочитанного
  файла; номера `N|` учитываются. При нескольких файлах и отсутствии совпадения путь
  больше не угадывается. После записи кеш чтения сбрасывается.
- Восстановление JSON не меняет запятые внутри строк и сохраняет исправленные аргументы
  в истории вызовов; обрезанные строки с кодом не восстанавливаются.
- Отсутствующий `new_text` отклоняется: пропущенный аргумент не означает удаление текста.
  Ошибки типов аргументов возвращаются модели как результат tools, не обрывают воркер исключением.
- SSE собирает имя инструмента из фрагментов. Некорректный вызов, незавершённый поток и
  ответ с `finish_reason=length` не исполняются как готовые команды.
- `tool_choice=required` сохраняется для generic профиля и преобразуется в `auto` только
  для Gemma 4, где требуется обход ошибки grammar/sampler.
- Достижение лимита шагов явно завершает ход как неполный, даже если часть правок записана.
- CMake следит за изменением `prompts/system.ru.txt`: промпт автоматически попадает в пересборку.

## Проверки на реальной модели

Опциональный бинарь `arli-live-eval` не включён в ctest и не запускается в offline CI:

```bash
build-ci/arli-live-eval http://127.0.0.1:8080/v1 /models/gemma-4-26B.gguf /tmp/arli-eval-report.json
```

Он создаёт отдельные временные папки, проверяет точное содержимое файлов и отсутствие
лишних файлов. Подтверждения опасных действий автоматически отклоняет. Каждый сценарий
имеет таймаут 8 минут. Отчёт обновляется после каждого сценария. Для отдельного задания
передай четвёртым аргументом `bugfix`, `multi_file`, `recovery` или `long_turn`.

Два полных прогона прошли 4/4 каждый. Результаты финального прогона:

| Задание | Вызовы tools | Записи | Ошибки tools | Сжатия |
|---|---:|---:|---:|---:|
| Исправление ошибки сложения | 3 | 1 | 0 | 0 |
| Согласованная правка двух файлов | 7 | 2 | 0 | 0 |
| Продолжение после чтения отсутствующего файла | 4 | 1 | 1 ожидаемая | 0 |
| 16 отдельных правок с чтением результата | 33 | 16 | 0 | 15 |

Это проверка конкретных сценариев, а не гарантия безошибочного выбора действий для любого
задания. Определение намерения остаётся консервативной эвристикой. В сводке ранние длинные
указания ограничиваются по размеру; полный текст текущего задания сохраняется отдельно.
История между ходами содержит пользовательские и итоговые сообщения, поэтому перед новой
правкой промпт требует свежего чтения, а не доверия к прошлому отчёту.
