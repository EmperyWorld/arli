# Редактирование и проверка результата

Изменения 0.5.4 закрывают цепочку отказ редактора → проверка старого файла →
неподтверждённый итог, разобранную в [инциденте диалога 18](audit-2026-10-10/dialog18-edit-incident.md).
Они не заменяют поведенческие тесты проекта и не доказывают завершение всех задач аудита.

## Строгая замена фрагмента

Для локальных изменений модель получает `replace_text`:

```json
{"path":"src/apps/terminal.js","old_text":"const oldValue = 1;","new_text":"const oldValue = 2;"}
```

Все три поля обязательны и имеют строковый тип. `path` задаётся явно,
`old_text` должен быть непустым и встречаться ровно один раз. `new_text=""`
означает явное удаление фрагмента. Нечёткий поиск и подбор пути не применяются;
LF из `read_file` сопоставляется с CRLF исходника без изменения остальных байтов.

Перед записью нужно прочитать все строки заменяемого фрагмента через `read_file`
в текущем ходе. Проверяются прочитанный снимок, единственность совпадения и синтаксис
собранного файла. Снимок повторно сравнивается перед публикацией. Успешная запись
сохраняет резервную копию и требует нового чтения перед следующей правкой.
Отказ синтаксического анализатора не изменяет файл или резервную копию.

Существующие `edit_file` с диапазонами строк и `append_file` сохраняются.
`replace_text` также подчиняется `read_only`, правилам workspace и учёту изменений.

## Диагностика и неприменённые операции

Для JavaScript диагностируется собранный кандидат: режим разбора, путь, строка и
небольшой контекст. Ошибка CommonJS на `export` или `import` не скрывает настоящую
ошибку ES-модуля. Когда режим неизвестен и оба анализатора отвергают код,
показываются обе подписанные диагностики.

`check_file` проверяет текущее содержимое. Его успех не закрывает отклонённую правку.
Неприменённая операция хранится отдельно: путь и отпечаток старого фрагмента либо
диапазон. Соответствующая успешная правка закрывает операцию; посторонняя запись
того же файла её не закрывает. Это проверка применения фрагмента, а не доказательство
того, что смысл изменения верен.

`abandon_edit(path, reason)` явно оставляет правку невыполненной. Она остаётся в
сохранённом состоянии и частичном итоге. Тексты исходников и замен не сохраняются
в этом состоянии учёта. При повреждении или переполнении состояния полное выполнение
не подтверждается.

## Подэтап и продолжение

После исследования проекта модель может вызвать:

```json
{"title":"Команды терминала через файловый API","checks":["node ./tests/terminal.cjs"],"remaining":["Перевести Explorer на файловый API"]}
```

Это аргументы `task_stage`. `checks` содержит 1–4 точные команды, которые нужно
выполнить через `run_shell` после последней правки. `remaining` перечисляет работу
за пределами выбранного подэтапа. Изменение файлов сбрасывает результаты проверок;
фоновый запуск не считается успешно выполненной проверкой.

Подэтап и неприменённые правки сохраняются в состоянии диалога и передаются в
следующий ход работы, включая «Продолжаем». Прошлые проверки не восстанавливаются
как успешно выполненные в новом ходе. Непроверенный подэтап нельзя молча заменить.
Если проверка недоступна или пользователь сменил задачу, `defer_task_stage(reason)`
сохраняет подэтап отложенным и позволяет выбрать новый. Возврат к нему выполняется
через те же `title` и `checks`; успешная проверка снимает соответствующее отложенное
обязательство.

Для изменений кода итог формируется из зарегистрированных файлов, выполненных
команд и оставшихся обязательств. Завершение хода (`Done.outcome`) и подтверждение
результата (`Done.verification_state`) остаются отдельными состояниями: завершённый
ход может иметь частично подтверждённый результат.

Ограничение: команды и охват подэтапа выбирает модель. Успешная команда, особенно
проверка одного синтаксиса, не доказывает полноту исходной задачи. Поведенческие
проверки должны покрывать новые функции и вызывающий их код.

## Температура и Node

В настройках модели доступна температура: `-1` сохраняет значение профиля,
`0..2` задаёт его явно, включая `0.0`. Сейчас значение профиля Gemma — `1.0`,
generic — `0.2`. Недопустимые и нечисловые значения отвергаются. Старый gRPC-клиент,
не передающий поле, сохраняет настройку. Поставленная в очередь задача сохраняет
своё значение и передаёт его агенту через `ClaimTask`, независимо от последующих
изменений настройки. Температура 0.0 не заменяет проверку результата.

Node не входит в продукт. Используется установленный исполняемый файл из
`/usr/bin`, `/bin`, `/usr/local/bin` либо последней по числовой версии установки
`~/.nvm/versions/node`. Файлы внутри workspace и указывающие на них ссылки исключены.
В bubblewrap подключается только бинарник, read-only, как `/run/arli/bin/node`;
домашний каталог не подключается. Окружение команды очищается, включая
`NODE_OPTIONS` и секреты. Установка npm и дополнительных сред выполнения этим
изменением не обеспечивается.

## Приёмка версии

Регрессии включают четыре исходных ошибочных патча диалога 18, строгую замену,
учёт неприменённых правок, сохранение подэтапа, передачу температуры и настоящий
Node внутри bubblewrap. Полный CI и двухходовый прогон реальной Gemma выполняются
отдельно; наличие этих тестов не означает, что текущий кандидат выпуска уже принят.
Результаты выпуска фиксируются после завершения прогонов.

Для изолированного состояния CTest можно передать CMake
`-DARLI_TEST_STATE_DIR=/tmp/arli-ci-state`; по умолчанию используется
`<build>/test-state`. Это позволяет отделить тестовые записи от пользовательского
состояния и, при необходимости, от файловой системы каталога сборки.
