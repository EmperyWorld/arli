# Оркестратор и воркер

Три процесса на одном хосте. Облака нет.

| Процесс | Бинарь | Роль |
|---|---|---|
| Оркестратор | `arli-daemon` | `Agent` + `AgentHub` на `127.0.0.1:4792`. Очередь, Claim, relay, аудит, spawn воркера. |
| Воркер | `arli-agent` | LLM и tools. Один `AgentHub.Session`. |
| Оболочка | `arli-shell` | Окно. Ходит только в `Agent` с `ui_token`. |

## Ход

1. `Send` пишет задачу `queued`. Второй `Send` в тот же диалог — `FAILED_PRECONDITION`. Между диалогами очередь FIFO.
2. Диспетчер делает CAS в `running` и шлёт `ClaimTask` (текст, workdir, адрес модели, ключ, списки shell).
3. Воркер ведёт ход и шлёт Thought, Token, Action, Observation, ConfirmNeeded, AskUser, Status, Done.
4. Оркестратор сохраняет каждый payload (включая Token и snapshots) в журнал `events`. Отдельно сохраняет отображаемые шаги в `steps` и `audit/{task_id}/events.jsonl`. Потоки оболочки читают журнал постранично.
5. `ConfirmDanger` возвращается воркеру как `ConfirmResult`. Пока решения нет, ход стоит.
6. Терминальный статус `done`, `failed` или `cancelled` повторно не пишется.

Обрыв стрима оболочки ход не отменяет. `AttachTurn` отдаёт сохранённые события, затем новые, до терминального состояния. Статус завершения и последнее событие фиксируются одной SQLite-транзакцией. При старте daemon прерванные задачи получают durable Error(reconcile_startup); исполнение их действий автоматически не повторяется.

### Восстановление потока (schema 9)

- `TurnEvent.task_id` идентифицирует задачу; `event_id` — монотонный ID записи журнала (глобальный в данной базе, не обязательно подряд внутри задачи).
- `AttachTurn(dialog_id, task_id, after_event_id)` возвращает события строго после указанного ID. Явный task_id позволяет подключиться и к завершённой задаче. С task_id=0 сохраняется старое поведение: поиск активной задачи диалога.
- after_event_id=0 означает выдачу с начала. Чужой или неизвестный ненулевой ID отклоняется. История до введения журнала доступна через OpenDialog/GetTurnTrace; отсутствовавшие Token-события задним числом не восстанавливаются.
- `Send.request_id` — необязательный ключ в пределах диалога, до 128 печатных ASCII-символов без пробелов. Повтор с тем же текстом подключается к той же задаче, включая завершённую; другой текст с тем же ключом даёт ALREADY_EXISTS. Send также принимает after_event_id. Новое задание должно начинаться с after_event_id=0.
- Ключ хранится в tasks, защищён уникальным SQLite-индексом и переживает перезапуск daemon. Пустой ключ сохраняет прежнее поведение Send без дедупликации. Удаление диалога удаляет его ключи и журнал.
- Чтение страниц ограничено 64 событиями и примерно 4 MiB JSON; одно крупное событие возвращается отдельно. Медленный UI блокирует только свой RPC, а не обработчик Session/watchdog. Общие quotas/retention журнала пока не реализованы.
- Qt создаёт request_id перед первой отправкой, запоминает последний event_id и допускает до четырёх попыток подключения с ограниченной паузой. Поддержка проверяется через `Health.event_resume_supported`; со старым daemon автоматический повтор Send запрещён. После исчерпания попыток отображается ошибка; задача продолжает выполняться на daemon.
- AskUser несёт `question_id`; оболочка возвращает его в AnswerAskUser, daemon и worker отклоняют несовпадение. Пустой question_id поддерживается для старых клиентов и не даёт такой защиты от запоздалых ответов.
- `interaction_active` — подсказка на момент доставки AskUser/ConfirmNeeded. Исторические закрытые запросы не открывают баннер. Перед принятием ответа сервер повторно проверяет актуальность; доставка события сама по себе не выдаёт разрешение.

Регрессия `stream-resume` проверяет отключение клиента, повторный Send, завершённый AttachTurn, восстановление после перезапуска, порядок и идентичность payload, старые question_id, страницы журнала, откат terminal transition при ошибке записи и неблокирующую работу с не читающим клиентом. `arli-live-stream-eval` — отдельный opt-in прогон через реальные daemon/agent и настроенную LLM.

## Watchdog

Каждые 250 мс: `waitpid` без зомби, подъём воркера с паузой 0.5 → 5 с. Hello не пришёл за 15 с — процесс убивается. Такой запас не убивает здоровый холодный старт при высокой нагрузке. Обрыв сессии: активная задача `failed(worker_lost)`, очередь ждёт нового воркера.

Таймауты из настроек: `idle_timeout_sec` (молчание, по умолчанию 600), `turn_timeout_sec` (2700), `cancel_grace_sec` (10). `Cancel` просит воркер остановиться; по истечении grace — `SIGTERM`, через 3 с `SIGKILL`, затем новый воркер. `HardStop` убивает сразу. Пока воркер помечен обречённым, новая задача ему не уходит.

Старт демона: все `queued` и `running` становятся `failed(reconcile_startup)`. `SIGTERM`/`SIGINT` демону — `Shutdown` воркеру и выход в пределах 5 с.

## Состояние

`ARLI_STATE_DIR` или `$XDG_DATA_HOME/arli` (иначе `~/.local/share/arli`):

| Путь | Кто пишет | Что |
|---|---|---|
| `arli.db` | демон и воркер | SQLite WAL. `messages` — воркер. `tasks`, `steps`, `settings` — оркестратор. Файл `0600`. |
| `ui_token`, `internal_token` | демон при первом старте | `0600`. В логи и аудит не попадают. |
| `workspace/` | инструменты | workdir по умолчанию |
| `audit/{task_id}/` | оркестратор | `events.jsonl` (вывод до 4 КБ, без секретов) и `task.json` |
| `arli.log` | демон и воркер | строка `ts level component key=value`, ротация 5 МБ |

`ARLI_LOG=debug|info|warn|error`.

Аудит лежит вне workdir: инструменты его не видят.

### Поколения AgentHub.Session

Каждое принятое соединение получает внутренний монотонный generation. Reader,
writer и teardown работают только с этим поколением: старый RPC не может забрать
Claim из очереди нового соединения или завершить его задачи. Watchdog фиксирует
поколение перед reap/kill и завершает только его. Значение не передаётся клиентом,
не меняет wire-протокол и не является заменой local credentials + bearer.

Первый frame обязан быть Hello с непустым worker_id (до 128 печатных ASCII символов
без пробелов), положительным pid и нулевыми task/dialog/turn. Повторный Hello,
пустой payload и некорректные рабочие frames завершают RPC. PID здесь проверяется
по формату, а не используется как доказательство личности процесса.

Heartbeat обновляет только текущую задачу при совпадении task/dialog/turn.
Запоздалый heartbeat игнорируется: отдельный heartbeat thread может отправить
его одновременно с Done. Он не обновляет таймер полезного прогресса.
Durable acknowledgement команд и повтор Claim после потери подтверждения
этим изменением не реализованы.

### Подтверждение Claim (schema 10)

Новый worker сообщает `Hello.claim_ack_supported`. Для него оркестратор создаёт
`command_receipts` (только id/task_id/status, без payload и ключа модели) перед
отправкой Claim с `OrchToWorker.command_id`. Worker резервирует выполнение и
отвечает `CommandAck`; положительный ACK означает принятие, а не завершение
инструментов. Оркестратор сохраняет accepted/rejected в SQLite.

Если ACK потерян, Claim повторяется с тем же номером и содержимым через 3 секунды,
не более трёх отправок. Cache worker возвращает прежний результат для идентичного
повтора. Более старый номер или изменённое содержимое под тем же номером не запускает
ход. После исчерпания попыток — failed/claim_ack_timeout и остановка worker.
Старому worker отправляется прежний Claim без command_id и без повторов.

Повторы разрешены только внутри живой Session. При потере Session задача
завершается worker_lost; незавершённая квитанция становится unconfirmed.
При восстановлении после аварии это также выполняется вместе с завершением задачи.
Claim не воспроизводится после перезапуска: worker cache не является durable,
а уже выполненные инструменты не имеют общей транзакции с ACK. Этот контракт
не обещает exactly-once для внешних побочных эффектов после аварии.

Ответы ask_user и ConfirmResult расширены подтверждениями ниже. Cancel и Shutdown
используют прежнюю доставку с ограниченным ожиданием и остановкой процесса через watchdog.


### Подтверждение ответов и разрешений

Hello.interaction_ack_supported согласует поддержку отдельно от Claim. Новый
оркестратор присваивает ответу/решению command_id и сохраняет квитанцию в той же
таблице command_receipts без текста ответа, токена разрешения и иных payload.
Reply.ok RPC по-прежнему означает постановку в relay; новое поле command_id
позволяет идентифицировать доставку. После ACK поток задачи содержит статус
«Ответ получен агентом» либо «Решение по разрешению получено агентом», который
отображается существующим Qt обработчиком и сохраняется для replay.

Worker применяет ответ или решение и пишет ACK под общим mutex отправки, прежде
чем разблокированный ход сможет отправить Observation/Done. Cache последних 64
доставок отвечает на повторы без повторного применения; вытесненные номера
никогда не исполняются заново. Повтор через 3 секунды, максимум три отправки.
Неподтверждённая доставка завершает задачу interaction_ack_timeout и останавливает
worker. Отмена пользователя имеет приоритет над этим таймаутом. При потере
Session квитанция unconfirmed; автоматического повторного разрешения в новой
Session нет.

Старый UI с пустым question_id сохраняет прежнюю семантику ответа на текущий вопрос;
при отправке worker relay подставляет фактический pending_question_id. Это не
позволяет определить намерение запоздалого старого клиента, поэтому строгая защита
от ответов на предыдущий вопрос требует question_id (новый Qt его передаёт).
Ответ ограничен 16 KiB. Полученный текст ask_user передаётся модели буквально:
без служебного OK и без обрезки внутри результата этого инструмента.

### Бюджет LLM-запроса

Перед сетевым запросом worker оценивает итоговые wire messages (после преобразования
Gemma), tools, response_format и добавленную template guide. Резерв ответа —
четверть настроенного окна, максимум 8192 для Gemma и 4096 для generic, минимум 256.
Для loopback llama.cpp агент перед каждым запросом вызывает `/apply-template`, затем
`/tokenize`, калибрует оценку по реально выбранному chat template и повторно
укладывает историю в бюджет. Внешний OpenAI-compatible provider без этих расширений
использует консервативную оценку и последующую калибровку по provider usage.
Сжатие истории использует оставшуюся часть окна. Если закреплённые system/task
instructions не помещаются, CONTEXT_LIMIT возвращается до HTTP без повторных
сетевых попыток и без удаления этих инструкций.

Расчёт консервативный: serialized UTF-8 bytes / 4 + 256 на шаблон, с коэффициентом,
который повышается по фактическому prompt_tokens провайдера. Это не точный
токенизатор модели; response_format может применяться сервером только как grammar
и потому завышать оценку. Само по себе прохождение локальной оценки не доказывает
границу фактических токенов для произвольного провайдера. Новый default — 16384;
сохранённые настройки не мигрируют автоматически. Окно следует задавать не выше
реального ограничения inference-сервера.

SSE запрашивает include_usage. Usage чанки с пустым choices также обрабатываются.
ContextUse.provider_reported отличает фактический prompt_tokens от локальной оценки;
reserved_output_tokens и completion_tokens передаются отдельно. Qt показывает
оценку со знаком ≈. Схемы и правила не исключаются из запроса ради прохождения guard.

### Правила workspace

Worker автоматически читает AGENTS.md в корне workdir до первого запроса к LLM.
Перед инструментом загружаются AGENTS.md предков его path, source/destination и
paths; для инструментов каталогов учитывается сам указанный каталог. Содержимое
передаётся в закреплённом system block с явными source/scope. Вложенные правила
применяются только к своему поддереву и не отменяют системные ограничения,
подтверждения или явное задание пользователя.

Новый/изменённый scope останавливает запланированные tool calls текущего batch с
RULES_UPDATED. Следующий запрос видит правила целиком и может повторить действие.
В том числе чтение/список откладываются: это не даёт заранее запланированному
действию игнорировать запрет из ещё не увиденного AGENTS.md. Правила не обрезаются
при compaction; общий request budget при необходимости явно отказывает.

Каждый tool step перечитывает уже обнаруженные scopes. Новый ход создаёт loader
заново и получает актуальные файлы. Чтение использует openat/O_NOFOLLOW, regular
file validation, UTF-8 и ограничения 32 KiB на файл, 128 KiB/64 файла на набор.
Абсолютные пути, .., симлинки в области правил и ошибки чтения запрещают операцию.
RULES_ERROR останавливает дальнейшее обращение к модели и не становится успехом.
Обычные tool outputs не становятся правилами.

Это загрузка AGENTS.md для путей файловых инструментов. Она не анализирует
произвольный код shell-команды, не загружает инструкции выше workdir и не является
атомарной транзакцией правил вместе с последующей файловой записью. Гарантии
самих mutation paths и внешние изменения файлов относятся к отдельному A17.

Рабочий процесс сохраняет ограниченную историю инструментов в `messages` с внутренней
ролью `context_state`. `list_messages` исключает её до применения LIMIT, поэтому она
не отображается в UI и не вытесняет обычную переписку. Снимок привязан к каноническому
workdir и восстанавливается в начале следующего хода; другой каталог его не получает.
Хранятся только tool, ok, turn_id и пути: без содержимого файлов, команд и ответов
пользователя. Это исторические данные, не инструкции и не доказательство текущего
состояния файлов. Снимок ограничен 32 действиями / 16 KiB, вытеснение отмечено явно.
Запись выполняется после получения результата инструмента; авария между изменением
файла и записью снимка может оставить историю неполной. Это не журнал транзакций файлов.

Схема 11 добавляет `dialogs.instructions`. `SetDialogInstructions` заменяет полный
текст (до 16 КиБ, пустой снимает правила) под тем же mutex, что постановка задачи.
Оркестратор сохраняет правила в `tasks.config_json` в момент enqueue; изменение
диалога не меняет уже отправленную задачу. `ClaimTask.dialog_instructions` передаёт
этот снимок агенту. `Hello.dialog_instructions_supported` обязателен для задачи
с непустыми правилами; старый агент получает явный `worker_capability_missing`
вместо исполнения без правил. Старые задачи без поля сохраняют прежнее поведение.
Работник не меняет правила. Они закреплены целиком в контексте и участвуют в
разборе явных запретов; произвольное содержательное требование всё ещё исполняет
модель, а не универсальный валидатор. Автоматического извлечения правил из
переписки нет. Правила принадлежат диалогу; смена рабочего каталога их не снимает.

Файловая публикация создаёт случайный O_EXCL temporary inode через открытый dirfd,
отвергает symlink-компоненты при обходе родителей и symlink-назначения, делает fsync
файла и каталога. Для замены проверяются ожидаемые байты, inode/ctime и неизменность
содержимого перед renameat; повторно сверяется родительский каталог. Сохраняются
uid/gid, обычные permission bits и xattr (включая ACL); setuid/setgid и file capabilities
не переносятся. Ошибка копирования атрибутов останавливает замену.
`PUBLISHED_UNSYNCED` означает, что имя уже опубликовано, но durability не подтверждена:
это ошибка с возможным эффектом, а не обещание «файл не изменён».

Резервная копия обязательна перед edit/append и перезаписью copy/move/delete:
ошибка копирования/проверки останавливает действие. `state/backups/` содержит latest
и отдельные случайно именованные `.history-*` версии; обе записи атомарны и проверяются.
Restore читает latest, отдельно сохраняет текущие байты в history (не меняя latest)
и публикует восстановление атомарно. Чтение для публикации/backup ограничено 64 МиБ.
Пока это не changeset-транзакция: финальный check→rename имеет остаточную гонку с
несогласованным внешним writer; move/delete ещё не переведены целиком на dirfd;
backup теперь вне workspace; changeset-журнал и retention ещё не реализованы.

### Проверка результата изменения файлов

Перед изменяющим ходом worker отдельным вызовом модели формирует неизменяемый
план буквальных файловых критериев (равенство байтов, наличие/отсутствие текста,
отсутствие файла, диапазон строк). Модель не получает инструменты исполнения на
этом шаге. Перед принятием финального ответа worker заново читает файлы и проверяет
критерии; нарушение возвращается модели для исправления, после двух неудачных
продолжений ход завершается failed. Успешная мутация инвалидирует предыдущую проверку.

Done дополнен verification_state, checked_revision и verification_plan_json.
checks_passed означает прохождение сформированных критериев, а не доказательство
полноты интерпретации запроса. partial/unverified явно обозначают неполную проверку.
План формирует модель, поэтому она может пропустить требование; команды, порядок
операций и смысловая корректность кода такими предикатами не доказываются.
План пока сохраняется в терминальном событии, не в журнале до первой мутации.


Session принимает только актуальный launch credential spawned worker и Hello
с ожидаемым PID. Missing/invalid/duplicate launch metadata отклоняется до
try_attach_session, не затрагивая действующую Session. Регистрация секрета и PID
защищена mutex на время `posix_spawn`: ранняя аутентификация ребёнка ждёт
регистрации в parent. В многопоточном daemon между созданием процесса и `exec`
не выполняется код приложения; worker применяет свои rlimits сразу в новом
образе, до открытия БД и подключения к Session. См. docs/05-secrets.md.


### Фоновые команды

Worker запускает отдельный arli-job-supervisor из того же каталога исполняемых
файлов. Supervisor получает очищенные argv/env через закрытый socketpair;
команда не стартует до записи jobs в SQLite и подтверждения worker. Команда
по-прежнему исполняется агентской стороной, не оркестратором. Supervisor переживает
завершение worker, владеет дочерней группой процессов и записывает код выхода в
служебный файл; ListJobs/StopJob переносят итог в БД.

Schema 12 добавляет jobs.process_identity (boot_id + /proc starttime) и exit_code.
StopJob открывает pidfd, проверяет сохранённую идентичность и сигналит только через
pidfd. Старые записи без идентичности становятся lost и не могут послать сигнал.
Лог каждого задания ограничен текущим и предыдущим файлом по 1 МиБ. Каталог задания
создаётся с mode 0700 в служебном state/jobs. Supervisor не получает токены/ключи модели.

ListJobs(include_finished=true) возвращает также завершённые задания с exit_code/exit_code_known; по умолчанию сохраняется список только активных.


Startup socketpair использует неблокирующие send/recv и единый deadline 5 секунд
на весь обмен: частичный прогресс не продлевает ожидание. Это deadline IPC, а не
всех системных вызовов fork/SQLite. Обёртка shell сохраняет ошибку завершающего
foreground выражения; при нулевом статусе учитывает результат последнего
асинхронного child ($!). Она не агрегирует коды всех параллельных shell jobs.

Файловые инструменты запрещают канонические пути внутри state, кроме
`state/workspace`; удаление/перемещение каталога-предка state также запрещено.
Рекурсивные списки пропускают служебное дерево и ссылки на него. При выборе
предка state как workdir shell/rg/Git маскируют всё дерево state; для работы с
дефолтным проектом следует выбирать непосредственно `state/workspace`.
`rg_search` запускает фиксированный argv с `--` перед шаблоном, без shell.
Git и rg используют общий read-only bubblewrap, очищенное окружение, запрет сети,
ограничения вывода и времени; Git отключает external diff, textconv и fsmonitor.
Это не защита от заранее созданных hardlink-копий секретов вне state или другого
процесса того же UID. Общая фильтрация секретов в логах/событиях остаётся отдельной
незавершённой задачей A01.

Standalone worker загружает gRPC registry перед каждым Claim из
`state/grpc-tools/registry.json`. Отсутствие каталога отключает provider; любой
существующий, но неверный реестр завершает task с GRPC_REGISTRY_INVALID до LLM.
Daemon не интерпретирует контракты и не исполняет RPC приложения. Один turn держит
собственный неизменяемый provider; изменения применяются к следующему Claim.

Каталог принадлежит UID worker и не имеет group/other permissions (0700), файлы
также приватны (0600), regular, без symlink/hardlink. Все ссылки на файлы — basename
в этом же закреплённом dirfd. Формат version=1, methods — максимум 32 записи:

```json
{"version":1,"methods":[{"tool_name":"grpc_write","endpoint":"127.0.0.1:50051",
 "method":"example.App.Update","descriptor_file":"app.pb","token_file":"app.token",
 "mutating":true,"deadline_ms":5000}]}
```

`app.pb` — binary FileDescriptorSet с imports; `app.token` — service-specific
bearer token (допускается один завершающий LF). Обязательны явные mutating и
 deadline_ms; адрес numeric loopback и unary method проверяет provider. Unknown
fields запрещены. Registry ≤128 KiB, descriptor ≤4 MiB, token ≤8 KiB, общий бюджет
чтения ≤16 MiB. Модель/UI/Claim не выбирают registry path и не получают credentials.
Для согласованной ротации оператор готовит целый приватный каталог и атомарно
заменяет поколение между заданиями; in-place правки во время чтения не поддержаны.
Доступ к state закрыт файловым инструментам и sandbox, но это не изоляция от
другого процесса того же UID. Нельзя помечать изменяющий метод mutating=false:
это доверенная классификация оператора, не вывод из protobuf.

Background logs фильтруются supervisor до записи и ротации через общий credential
fingerprint Stream. Launcher передаёт только путь ledger; окружение дочерней
команды остаётся прежним allowlist. Удерживаемый хвост не превышает длину самого
длинного зарегистрированного значения и может ждать нового вывода/завершения.
Forced stop отбрасывает этот хвост. Ошибка log/filter приводит к завершению owned
process group и lost вместо успешного terminal результата. Обе ротации ≤1 MiB и
содержат только целые UTF-8 фрагменты.

Schema 13 добавляет jobs.dialog_id/task_id/turn_id с default 0 и индекс owner.
Claim handler передаёт task_id через TurnControl; run_turn передаёт свои dialog/turn
через ShellRunOptions. Эти поля не являются аргументами модели. DB проверяет,
что ненулевой task принадлежит dialog/turn и ещё running, до разрешения supervisor
начать команду. Нулевые ID обозначают legacy/standalone запуск без этой связи.
Job owner сохраняется как исторический ID, без каскадного удаления процесса/строки
при удалении диалога. Завершение исходного хода само по себе не останавливает job.

ListJobs расширен optional dialog_id/task_id (0 — прежний global list); оба фильтра
применяются в SQL до LIMIT. JobInfo возвращает все три ID. StopJob может передать
expected_dialog_id/expected_task_id: несовпадение не посылает сигнал. Нулевые
expected поля сохраняют прежнее поведение. Это consistency check одного локального
оператора, а не новая multi-user authorization boundary; доступ всё ещё по ui_token.

Одновременно допускается до 16 running jobs, до 8 на dialog и до 4 на task
(`job_policy.hpp`). Unowned jobs учитываются в global limit. Быстрый preflight
предотвращает создание лишнего supervisor; окончательное условие COUNT встроено
в INSERT SELECT и проверяется атомарно между соединениями SQLite. Завершение job
освобождает слот. При заполнении квоты инструмент возвращает JOB_QUOTA либо
JOB_ADMISSION_REJECTED, без запуска пользовательской команды.

JobMaintenance в daemon сверяет running jobs независимо от UI и LLM health:
до 64 записей за проход, раз в секунду, с cursor для legacy наборов больше лимита.
Читаются result sidecar и process identity; stale PID становится lost без сигнала.
Partial index jobs_running не даёт истории завершённых jobs замедлять этот обход.
Перезапуск daemon подхватывает результаты, появившиеся, пока он не работал.
Остановка daemon не останавливает jobs; хранение terminal истории/logs пока не
ограничено общей retention policy (индивидуальные log rotations ограничены).

### История фоновых задач (schema 14)

`jobs.finished_at` фиксируется единожды при переходе из running в terminal и
передаётся additive полем JobInfo.finished_at. Старые terminal rows при миграции
получают текущее время, чтобы возрастная очистка не удаляла их сразу.
Daemon JobMaintenance при старте и затем раз в 30 секунд обрабатывает до 32
terminal rows: хранит последние 128 записей, не старше 7 дней. Running rows и
записи с ещё живой process identity не удаляются. Ошибки/небезопасные пути
пропускаются и могут временно превышать лимит.

Очистка использует directory FD / O_NOFOLLOW и разрешает только приватный
state/jobs/job-XXXXXX с четырьмя известными файлами supervisor. Посторонние файлы
сохраняют весь каталог; symlink каталога не обходится. Запись БД удаляется после
успешного удаления файлов. Повтор после частичной очистки допустим. Ошибка
запуска до регистрации jobs очищает созданный каталог; аварийный kill в этом
окне покрывает отдельный orphan scan с описанными ниже leases.

Очистка брошенных каталогов использует отдельный bounded scan: до 64 directory
entries за проход, курсор живёт между проходами maintenance. Кандидат старше
60 секунд без jobs.log_path в БД очищается только по тем же строгим правилам
известных файлов. Launcher держит flock каталога jobs с момента до mkdtemp до
регистрации/GO; supervisor держит flock своего каталога до выхода. Scanner
использует неблокирующие locks, поэтому живой запуск/вывод не удаляет. После
SIGKILL locks освобождает ядро; orphan подбирается при следующем обходе. Grace
покрывает короткое окно старых supervisor без lease. Приватный каталог с
посторонними файлами сохраняется для ручного разбора, автоматического удаления
неизвестных данных нет.

Для старых относительных/alias log_path scanner также проверяет suffix
job-XXXXXX/output.log через индекс БД. Совпадение консервативно сохраняет каталог,
даже если старая запись указывает в другой корень: автоматическая очистка не
должна потерять зарегистрированную job из-за представления пути.

### Поток job log (additive WatchJobLog)

WatchJobLog принимает id, optional expected owner и opaque after_position;
JobLogChunk возвращает text, next_position, gap, terminal/status/exit code.
Клиент сохраняет позицию только после применения chunk. Пустая позиция начинает
с самой старой из двух сохранённых ротаций. Удалённая ротация даёт gap=true;
клиент показывает пропуск, а не притворяется, что получил весь вывод.
Позиция включает job ID, device/inode/birth time и raw byte offset, подписана
HMAC-SHA256 внутренним токеном. Она сохраняется при restart daemon, но становится
недействительной при смене internal_token; чужая job/подделка отклоняются.
Файловая система без statx birth time получает FAILED_PRECONDITION; legacy
ListJobs продолжает работать. Reader использует NOFOLLOW, проверку приватного
каталога, regular file/owner/nlink/size и snapshot двух поколений при rotation.

Сервер читает по 8 KiB raw, фильтрует credentials и UTF-8 между chunks и
поколениями; подтверждённая позиция исключает ещё удерживаемый фильтром хвост.
Один chunk ограничен 1 MiB с учётом расширения масок и финального flush.
Память не растёт за скоростью producer: старые данные могут быть потеряны только
с явным gap. До 8 подписок на daemon, каждая до 15 секунд; watchdog отменяет
также блокирующий Write медленному клиенту без deadline. Клиент переподключается
с последней применённой позицией после истечения lease/транспортного сбоя.
Cancel/deadline освобождает подписку, не останавливая саму job. NOT_FOUND означает
истёкшую/отсутствующую историю. Разрешения те же, что у ListJobs: UI bearer.

### Защищённое хранилище резервных копий

`state/backups/<SHA256(canonical workdir)>/<SHA256(relative path)>/latest` и
случайные `latest.history-*` отделяют проекты и поддерживают длинные имена файлов.
Каталоги backups/project/file — текущего UID, без group/other permissions;
существующий state root должен принадлежать UID и не разрешать чужую запись.
Каждый путь открывается без directory symlinks. Backup сохраняет metadata файла
за приватной границей каталогов; ошибки открытия/прав/публикации/проверки
останавливают мутацию. Tools и shell не получают прямого доступа к state/backups.
Restore читает только защищённый latest, сохраняя текущую версию отдельно.

Старые workspace `.arli-bak` не удаляются и не импортируются автоматически:
модель имела возможность изменять их байты. При отсутствии защищённой копии
restore_file явно отказывает; legacy backup можно отдельно проверить вручную.
Canonical alias того же workdir использует ту же историю; перемещение проекта
в другой canonical root создаёт другое пространство имён. Retention и откат
всего хода будут строиться поверх этого хранилища; пока это не changeset journal.

### Журнал публикаций одного хода

Worker создаёт MutationScope из trusted dialog/turn/task IDs на время run_turn.
До первой публикации журнал не создаётся. Atomic publication edit/append/create/
copy/restore записывает `state/changesets/<workdir hash>/turn-<random>/manifest.json`:
relative path, before_exists/hash/private snapshot, expected after hash, sequence.
Prepared manifest fsync-ится до публикации workspace файла; после rename/link
сохраняется applied/failed/uncertain. Повтор того же turn ID создаёт отдельную
attempt directory и не затирает старый журнал. Entries ограничены 4096, manifest
4 MiB. Содержимое файлов в JSON не копируется — только hashes и private references.

Ошибка prepared record запрещает публикацию. Ошибка outcome record после
публикации возвращает MUTATION_UNCERTAIN и запрещает дальнейшие записи этого
scope; durable prepared запись остаётся для последующей сверки. Реальный факт
rename/link учитывается отдельно от текста ошибки. Исходные байты после prepare
повторно проверяются publisher, поэтому внешняя правка в этом окне не затирается.
Crash до/после rename сохраняет prepared record + before snapshot; автоматического
дописывания истории или отката пока нет. Move/delete, прямые shell изменения и
RPC отката ещё не подключены; это журнал atomic file publications, не полная
транзакция всех эффектов хода. Check→rename race остаётся отдельной задачей.

Сверка аварийного журнала (`inspect_mutations`, worker library): принимает
canonical workspace и строго проверяемый changeset ID, читает только private
bounded manifest, проверяет version/ownership/path/hash/snapshot namespaces.
MutationScope держит exclusive flock каталога attempt; инспектор берёт shared
nonblocking lease и отказывает для активного хода. После crash lease снимает ОС.
Для последней не-failed записи каждого пути возвращает observation
before/after/unchanged/conflict/unavailable; прежние записи superseded, failed
остаются not_published. Before snapshot проверяется отдельно по SHA-256.
Это наблюдение bytes в момент чтения, не доказательство исполнения и не
разрешение перезаписи: prepared/uncertain phases не переписываются, одинаковые
before/after дают unchanged. Любое восстановление обязано повторно проверить
диск перед изменением. Пока это внутренний API; RPC/UI revert не подключён.

`revert_mutations` (worker library) держит exclusive lease исходного changeset,
проверяет dialog owner и сворачивает цепочки публикаций одного пути. Разрыв
before/after цепочки считается конфликтом. Возвращает per-file outcomes;
чужие bytes, symlink, недоступные/испорченные snapshots не перезаписываются.
Для безопасных по текущей проверке путей восстанавливает самый ранний original,
созданные ходом файлы удаляет с backup/expected/inode/parent checks и fsync.
Новый MutationScope журналирует откат и durable `reverts` ID; delete расширяет
внутренний manifest (`after_exists=false`, пустой after_hash). Сверка понимает
такие записи. Повторный запуск распознаёт уже восстановленные bytes; исходный
журнал не меняется. Откат самого отката использует тот же механизм.

Это последовательный, явно частичный откат: ошибка одного файла не скрывает
успехи других; report.complete=false при конфликтах/ошибках. Prepared после
аварии сверяется с actual before/after. Это не filesystem transaction/CAS:
остаточная check→rename/unlink гонка с несотрудничающим внешним writer остаётся.
Слияние чужих изменений внутри того же файла не выполняется: весь такой файл
оставляется пользователю. RPC/UI approval/selection ещё не подключены;
внутренний API не выдаётся модели и вызывается только trusted worker caller.

`Agent.RevertChangeset` ставит отдельную операцию в существующую tasks queue:
changeset ID хранится в config_json snapshot, передаётся additive Claim field,
worker Hello объявляет mutation_revert_supported. Старый worker отклоняется
до Claim; операция не превращается в LLM prompt. Request ID обязателен;
пересечение Send/Revert с одинаковым ID отклоняется, повтор одной операции
использует durable events/AttachTurn и не повторяет файловые действия.
Workspace/read_only берутся из snapshot; смена LLM endpoint не блокирует
операцию, которой модель не нужна. Оркестратор файлы не восстанавливает.

Worker проверяет source dialog и journal, затем всегда запрашивает ConfirmHub
через обычный relay (включая возможное удаление созданных файлов). Отказ/cancel
до approval не меняют workspace; после approval cancellation проверяется между
файлами. Worker пишет messages и выдаёт Observation/Done с честным outcome;
исходный журнал и журнал отката остаются источником recovery после аварии.
Открытие операции из Qt и discovery changeset IDs ещё не подключены.

### Индекс аварийных журналов

Для task_id>0 worker после prepared manifest и до первой workspace mutation
сохраняет fsynced private locator в changesets/<project hash>/tasks/<task_id>.
Неудача индексирования блокирует запись файла. До 64 attempts на task; lease
сериализует запись каталога. Metadata reader проверяет owner/private/nofollow,
размер locator и manifest, task/dialog/turn; активный journal lease исключается.
Daemon не читает workspace bytes/snapshots и не выполняет recovery tool.
GetTurnTrace для terminal task дополняет отсутствующий Done-локатор отдельным
TraceItem kind=changeset, не выдумывая успешное завершение. Ошибка каталога явно
показывается в trace. Журналы старых сборок без такого индекса автоматически
не перечисляются: известный changeset ID остаётся пригоден для worker API.

RevertChangeset.source_turn_id связывает UI-запрос с исторической задачей.
Её workdir snapshot переносится в новую задачу отката; текущие read_only и
остальная политика сохраняются. Claim несёт source task/turn IDs, worker
проверяет их по journal до подтверждения. Hello mutation_catalog_supported
отсекает старого worker без такой проверки. Дедупликация учитывает source turn.
Qt берёт source turn из выбранной карточки; TaskCard даёт доступ к шагам и
восстановлению даже когда авария оставила только сообщение пользователя.

### Идентичность workspace в очереди

Новые tasks snapshots сохраняют canonical absolute workdir и versioned
workspace_identity: существующий root (или ближайший существующий ancestor для
нового root), device major/minor, inode и statx birth time. Capture не создаёт
проектные файлы. Worker capability workspace_identity_supported обязателен для
таких Claim; старому worker проверка молча не отключается.

Worker открывает pinned ancestor без symlinks, сравнивает identity и создаёт
недостающие каталоги через mkdirat/openat/fsync от удерживаемого descriptor.
Существующие обычные descendants под тем же anchor допустимы; новые symlinks
не используются. На admission удерживается descriptor самого root. Проверка
повторяется перед rounds/tools/final acceptance и между файлами отката.
Изменения содержимого каталога не меняют birth time и не вызывают ложный отказ.
Замена/перенос root даёт WORKSPACE_CHANGED; файловые системы без statx inode/
birth time дают явный WORKSPACE_UNAVAILABLE. Это не filesystem CAS: гонка
между последней проверкой и конкретным syscall остаётся в A17.

Новые mutation manifests сохраняют actual root identity после создания папки.
Исторический revert наследует queued identity источника и отдельно проверяет
actual identity из журнала. Для legacy Claim/manifest без этих metadata
проверка начинается с admission и не доказывает состояние до старой постановки.

Процедурные критерии worker: `command_succeeds` засчитывает только точную команду
и успешный foreground result на текущей revision; новый файловый/gRPC mutation
инвалидирует её. `read_after_each_write` требует полного чтения указанного файла
после правки перед следующей мутацией; line coverage и hash берутся из read_file,
страницы разных версий не объединяются. Проверки не запускают команды сами и
не обходят UI approval. Отказ точной shell-команды запоминается до конца хода.
При запрете создания других файлов shell запускается с workspace ro-bind,
обязательным bubblewrap и без unsandboxed fallback; обычные разрешённые файловые
правки продолжают проходить через file tools. Private state metadata этим запретом
на файлы проекта не отключаются. Произвольный порядок и внешние эффекты не считаются
доказанными этими критериями и требуют явного unverified/partial.

Admission задач: максимум 64 queued/running и 8 MiB их text+config_json;
text/snapshot отдельно максимум 256 KiB. SQLite проверяет квоту атомарно с INSERT.
Terminal task освобождает активный бюджет, существующий request_id повторно
не ставится в очередь. Send/AttachTurn/RevertChangeset делят 16 мест на streams;
отказ — RESOURCE_EXHAUSTED с названием лимита. Место освобождается по завершении
серверного RPC. Write, заблокированный на 10 секунд, отменяет только stream;
нормальное ожидание модели и task execution продолжаются. Reconnect использует
прежние request_id/after_event_id. Health/Cancel/worker Session этим пулом не заняты.

### Страницы переписки (волна 36)

`OpenDialog.message_page_size` включает постраничный режим (1–100). Нулевое
значение сохраняет прежние последние 200 сообщений. Новый authenticated UI RPC
`ListMessages(dialog_id, before_id, page_size)` возвращает старшие ID меньше
исключительной границы, в возрастающем порядке внутри страницы; `next_before_id=0`
означает конец. Новые сообщения не сдвигают продолжение; удалённые записи могут
исчезать. Это последовательный обход неизменяемых сообщений, не снимок всей БД.
`context_state` не показывается. Default page size 50, maximum 100; soft byte budget
512 KiB, один большой элемент допускается до 3 MiB с envelope reserve. Более крупный
элемент даёт RESOURCE_EXHAUSTED, без усечения/пропуска текста. Partial index
`messages_history(dialog_id,id)` исключает context_state и поддерживает range seek.

Qt запрашивает 50 сообщений при открытии. Кнопка ранней истории добавляет страницу
в начало, блокирует повторное нажатие, сохраняет boundary при ошибке для повтора.
Generation выбранного диалога и модели отсекает устаревшие ответы; загрузка идёт
через control queue независимо от активного stream. Переполнение queue возвращает
видимую ошибку и снимает loading. Поиск/копирование явно относятся к загруженным
сообщениям. Старый демон, игнорирующий новые поля OpenDialog, продолжает открываться
без выдуманной границы продолжения. GetTurnTrace выдаёт стабильные страницы по
`TraceItem.row_id`: 50 по умолчанию, не более 100 и примерно 1 MiB. Клиент
продолжает с `next_after_id`; recovery-элементы без строки БД добавляются только
на последней странице. ListDialogs legacy ограничен, а новый ListDialogPage пагинирован.
OpenDialog включает только первую страницу последнего trace и её continuation cursor.

Подробные `events` и `steps` имеют дисковую retention: сохраняются данные последних
5000 terminal tasks и не старше 90 дней. Очистка идёт фоновыми пакетами по 128
задач. Метаданные task, сообщения диалога и request_id не удаляются, поэтому
переписка, terminal outcome и идемпотентность Send сохраняются; для старой задачи
может быть недоступен только подробный trace/replay.

### Страницы диалогов (schema 15, волна 37)

`ListDialogPage` — authenticated UI RPC с page_size 0→50, maximum 100 и opaque
page_token. Ответ содержит summaries без instructions, в прежнем порядке
updated_at DESC/id DESC. Table dialog_list_state и три SQLite triggers увеличивают
revision при insert/update/delete dialogs, в том числе при touch из worker process.
Один read statement получает revision и страницу из одного SQLite snapshot.
Продолжение со старой revision возвращает ABORTED/DIALOG_LIST_CHANGED: клиент должен
начать обход заново. Revision сохраняется при restart. Это обнаружение изменения,
а не долгоживущая snapshot-транзакция между RPC. Index dialogs_recency поддерживает
range query. Soft page budget 512 KiB; legacy title >256 KiB даёт явную ошибку.
Новые CreateDialog/RenameDialog ограничены 4 KiB UTF-8 и запрещают NUL.

Старый ListDialogs сохраняет полный ответ для небольших списков, но отказывает
RESOURCE_EXHAUSTED при >1000 строк или >3 MiB, без молчаливого усечения. Новый Qt
переходит на старый RPC только при UNIMPLEMENTED. Transient/auth/validation errors
не вызывают downgrade и не стирают уже показанные строки.

Поиск остаётся QString::contains(CaseInsensitive), поэтому Unicode поведение
сохранено без добавления зависимости в daemon. Qt последовательно сканирует
страницы до 50 совпадений или конца, хранит только совпадения, затем предлагает
загрузить следующие. Worst-case поиск остаётся линейным обходом по сети, а не
индексированным full-text search. Debounce 180 ms и generation отсекают старые
запросы; не более одного запроса на batch. При изменении списка требуется явное
обновление, чтобы активный worker не запускал бесконечные автоматические повторы.
