# Диалог 18: ошибки редактирования после установки Arli 0.5.3

Разбор 11 октября 2026. Реальная установленная сборка: `arli-0.5.3-1.fc44.x86_64`.
Демон запущен в 05:20:54 +10. Исследованы задачи 78 и 79, 05:21:45–05:26:35 +10.
Изучены SQLite в режиме read-only, audit/events, arli.log, журналы контейнера
`stack2-llama-chat`, текущие файлы, журналы изменений и резервные копии.
Исходники продукта, настройки, службы и рабочие файлы приложения при разборе не изменялись.

Подтверждена цепочка: неверно выбранный диапазон или текст → обоснованный отказ
редактора с неправильной диагностикой → ошибочные попытки восстановления → проверка
неизменённого файла снимает незавершённую правку → неподтверждённый итог принят.
Кроме того, одна успешно записанная правка сломала выполнение команд терминала.

с преждевременным завершением, а не доказанный бесконечный цикл.

## Подтверждённые дефекты Arli

1. **Неправильная диагностика JavaScript.**
   `src/daemon/tools/syntax_check.cpp:125–129` проверяет `.js` как CommonJS,
   затем как ES module. Если оба режима отвергают код, наружу уходит первая ошибка:
   `Unexpected token 'export'` на строке 4. Настоящая ошибка ESM теряется.
   Все четыре синтаксических отказа воспроизведены через Node 24.21.0 parse-only:
   опечатка на строке 109; отсутствующая скобка; два вложенных объявления метода.
   Правильное исправление сохраняет защиту записи, но возвращает диагностику
   подходящего режима, путь, строку кандидата и контекст. При неоднозначном режиме
   нужно честно показывать обе диагностики с подписями.

2. **Проверка старого файла подтверждает несостоявшуюся правку.**
   `src/daemon/verification.hpp:20–28` смешивает ошибки текущего содержимого
   и отклонённых кандидатов в одной map. `check_file` OK удаляет запись целиком.
   Standalone C++ воспроизведение с настоящим production header подтвердило:
   rejected candidate → pending; old-file check OK → pending исчезает.
   Нужно раздельно хранить состояние текущего файла и незавершённой операции.
   Проверка привязывается к ревизии; неприменённая операция закрывается корректной
   заменой соответствующего намерения либо явным отказом с причиной и неполным итогом.
   Произвольная успешная запись того же файла также не доказывает выполнение намерения.

3. **Нет проверки фактического результата выбранного подэтапа.**
   `src/daemon/turn.cpp:193–198` строит acceptance до исследования проекта,
   передавая текущий запрос и правила. Продолжение получает текст «Продолжаем»,
   без сохранённого проверяемого подэтапа. После исследования критерии не уточняются.
   В `plans` для диалога 18 записи нет. Сохранённые recent_actions — история действий,
   но не список обязательств и незавершённых изменений.
   Нужен конкретный подэтап после исследования, дополнение проверок без ослабления
   исходных требований пользователя и перенос незавершённого в следующий ход.

4. **Финальные утверждения не ограничены доказательствами.**
   `src/daemon/turn.cpp:868–950` принимает свободный итог после снятия pending;
   пустая acceptance не мешает `done`. Предупреждение `unverified` не предотвращает
   последующее «завершила рефакторинг» и приписывание изменений Explorer.
   Нужно отделять завершение исполнения хода от подтверждения пользовательской задачи.
   Сохранять совместимость arli.v1: дополнительные поля результата и UI-индикация,
   без переопределения старых полей/RPC. Честное частичное завершение допустимо;
   пустой список критериев не должен автоматически объявлять все задачи проваленными.

5. **Неудобный и несогласованный контракт редактора.**
   `prompts/system.ru.txt` требует точные `first_line`/`last_line`, но схема
   `src/daemon/tools.cpp:1128–1142` делает их необязательными.
   `read_edit_guard.hpp:149` проверяет их только при наличии. После отказа модель
   просто убирает поля. Прочитанность диапазона и свежесть не доказывают, что выбран
   правильный фрагмент. Предлагается отдельный строгий инструмент замены уникального
   старого текста с привязкой к прочитанной ревизии; legacy line API сохранить.
   Это уменьшает риск ошибочных координат, но не заменяет проверки поведения.

## Реальный результат и проверка воспроизведения

SHA256 всех четырёх изменённых файлов совпадает с after_hash журналов задач 78/79;
резервные копии совпадают с before_hash. Обнаруженная регрессия соответствует
зафиксированным действиям Arli.

На копиях Terminal и VirtualFS выполнен Node harness с DOM/localStorage-заглушками
в bwrap с отдельными namespace, без сети и доступа к пользовательским данным:

- Terminal до задачи 79: `help` работает, `ls` выводит `documents notes.txt`.
- Terminal после задачи 79: `help` и `ls` выбрасывают `ReferenceError: parts is not defined`.
- Контрольный вариант с восстановленным только `parts` в памяти: `help` работает,
  `ls` выводит `No such directory`. Независимая проверка `readdir('')` возвращает null.

Последняя ошибка осталась после двух отклонённых правок fs.js. Это не только проблема
формулировки ответа: фактическая функция приложения сломана.
Браузерный UI целиком не тестировался; эти проверки доказывают конкретные дефекты методов.

## Логи ЛЛМ и параметры

В контейнере llama-server за исследованный интервал 40 запусков и 40 завершений
генерации. Во всех записях завершения `truncated=0`, максимальный `n_tokens=24512`.
Настройка Arli `context_tokens=49152`; сервер запущен с контекстом 64000.
В просмотренном интервале нет сообщений error/failed/OOM/context shift.
Эти данные не указывают на переполнение контекста или падение сервера как причину.

Контейнерный журнал содержит служебную телеметрию, не полные тела HTTP-запросов.
Содержание действий и возвращённые инструментам результаты восстановлены по истории Arli.
Идентификатора для строгой корреляции каждого HTTP-запроса с task/step сейчас нет;
сопоставление сделано по времени. Диагностический режим должен сохранять безопасные
метаданные request_id, task/step, профиль, sampling, finish_reason и usage.

Для gemma4 клиент `src/daemon/llm_internal.cpp:59–69` задаёт temperature=1.0,
top_p=0.95, top_k=64, reasoning budget=2048. Параметр temperature=0.0 не применялся
к этим историческим запросам по конфигурации клиента; серверный argv также задаёт 1.0.
Полные исторические request bodies отсутствуют. Параметры нужно сделать явными,
а профиль 0.0 использовать для диагностического сравнения. Он не исправляет ошибки
диагностики, учёта правок или проверки поведения сам по себе.

## Решение и критерии приёмки

Первый пакет исправлений: корректная диагностика ESM + раздельный учёт отклонённых
операций и проверок текущего файла + итог, явно отражающий незавершённые изменения.
Затем строгая замена фрагмента, устойчивый подэтап между ходами и поведенческие проверки.
Свежесть чтения, атомарная запись, резервные копии, подтверждения и синтаксический guard сохраняются.

Обязательные регрессии:

1. Четыре исходных ошибочных патча отвергаются с настоящей диагностикой; файл и backup неизменны.
2. `rejected edit → check old file OK → final` не подтверждает выполнение правки.
3. Успешное исправление закрывает соответствующую операцию; посторонняя правка её не закрывает.
4. Синтаксически корректное удаление объявления `parts` обнаруживается поведенческой проверкой.
5. После «Продолжаем» сохраняются выбранный подэтап, незавершённые работы и проверки.
6. Итог не приписывает Explorer изменения без подтверждённых действий.
7. Реальная Gemma проходит двухходовый сценарий на исходной копии WebOS: Terminal
   help/ls/cat/touch/rm, корневой readdir, сохранение/чтение Notepad и Todo, список/открытие Explorer.
   Оценивается состояние и поведение приложения, а не число записей или текст ответа.
   В каждом прогоне должен быть честный статус при неполном результате.

Прежние 64/64 теста не покрывали связку отказ редактора → проверка старого файла →
ложный финал и данный многофайловый сценарий. `syntax_check_test.cpp:76–84` останавливался
на регистрации отказа, не проверяя его последующее неправильное снятие.
`turn_execution_test.cpp:21–24` явно допускает `done + unverified`. Это пробел приёмки.

Материалы воспроизведения находятся в `/tmp/arli-dialog18-investigation/`:
`evidence-summary.json`, `llama-server.sanitized.log`, `llm-metrics.json`,
`replay_rejected_syntax.py`, `syntax-replay.json`, `replay_verification.cpp`,
`verification-replay.json`, `runtime-proof.cjs`, `runtime-proof.json`.
В этой работе выполнен анализ и воспроизведение дефектов. Исправление продукта и новая
приёмка на модели ещё не выполнены; новая RPM не собиралась.
